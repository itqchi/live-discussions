# Live Discussions

Cross-platform live discussion rooms with Clubhouse-style roles, camera, screen sharing, reactions, comments, Houses, and first-class browser support.

## Architecture

- **Web:** Angular, standalone/lazy features, signals, typed reactive forms
- **Mobile:** React Native
- **API:** NestJS
- **Realtime media/data:** LiveKit
- **Persistence:** PostgreSQL for durable House/user data, with an in-memory fallback
- **Workspace:** Nx monorepo
- **Shared contracts:** `@live-discussions/contracts`

The Angular application is split by feature (`home`, `houses`, `rooms`) with page components delegating use cases to facades and data-access services. NestJS owns room identity, authorization, role resolution, and LiveKit token/permission issuance.

## Room lifecycle

Each room has two distinct identifiers:

- an immutable server-generated UUID used internally and as the LiveKit room name;
- a human-readable slug used by the browser route: `/room/<room-name>`.

Room slugs are generated by the API. Creating a room also creates its LiveKit room. Room-scoped application state is intentionally ephemeral and remains available only while the corresponding LiveKit room exists. LiveKit keeps a new room for up to five minutes before its first join and applies a 20-second departure grace period after a connection loss so a browser reload can reconnect safely. The API reconciles finished LiveKit rooms every five seconds.

Participant roles, Stage/Audience presence, room settings, bans, timed mutes, and shared comments are retained in API memory for the lifetime of the room. They survive a client reload but not an API restart or LiveKit room termination. An explicit Leave disconnects the client and asks the API to delete the room immediately when no connected participants remain. Closing a room force-deletes the LiveKit room and all of its application state. Browser clients remember whether a participant entered from Home or a House so Leave/Close returns that participant to the appropriate screen.

Client-side navigation from one room slug to another explicitly tears down the previous LiveKit session before joining the next room.

## Development identity

Authentication is currently development scaffolding. The web/mobile clients send:

- `x-dev-user-id`
- `x-dev-display-name`

The API owns all role/permission decisions; clients cannot choose their room role. These headers are **not production authentication** and must be replaced before treating the deployment as secure for untrusted users.

## Environment

Copy `.env.example` to `.env` and configure LiveKit:

```bash
cp .env.example .env
```

Required LiveKit variables:

```text
LIVEKIT_URL=wss://<project>.livekit.cloud
LIVEKIT_API_KEY=...
LIVEKIT_API_SECRET=...
```

Persistence defaults to memory:

```text
DATABASE_DRIVER=memory
```

For PostgreSQL:

```text
DATABASE_DRIVER=postgres
DATABASE_URL=postgresql://...
```

Room-scoped state is always ephemeral, independently of this setting. `DATABASE_DRIVER=postgres` makes Houses, House memberships, and user records durable; `DATABASE_DRIVER=memory` also keeps those records only for the current API process.

## Install and run

The repository targets Node `22.23.1` and npm `10.9.8`. A committed npm lockfile is the dependency source of truth, so use `npm ci` for reproducible installs.

```bash
npm ci
npm run api
npm run web
```

Useful commands:

```bash
npm run check            # operational script checks + contracts/web/API build + mobile typecheck
npm run build:web
npm run build:api
npm run build:contracts
npm run typecheck:mobile
npm run migrate:api      # applies PostgreSQL migrations; no-op in memory mode
npm run mobile           # Metro bundler
npm run mobile:ios       # preflights the native iOS host project described below
npm run mobile:android   # preflights the native Android host project described below
```

CI and Render builds also use `npm ci` so they install the dependency graph recorded in `package-lock.json` rather than resolving a new graph on each build.

## React Native hosts

The repository commits both native host projects under `apps/mobile/ios` and `apps/mobile/android`. It also includes the React Native application, Nx targets, LiveKit dependencies, and `registerGlobals()` setup.

- Android initializes `LiveKitReactNative`, declares camera/microphone/audio and media-projection permissions, and is compiled as a debug app in CI.
- iOS initializes `LivekitReactNative` and declares camera and microphone usage descriptions.
- iOS screen sharing still requires a Broadcast Extension before it is complete on a physical device.

`npm run mobile:ios` and `npm run mobile:android` validate the native host before delegating to the Nx React Native targets.

The mobile join screen makes the API base URL editable. Its development defaults are:

- Android emulator: `http://10.0.2.2:3000`
- iOS simulator: `http://localhost:3000`

A physical phone must use a reachable LAN address or the hosted API URL instead of localhost.

## Database migrations

Ordered migrations live in `apps/api/migrations`.

`npm run migrate:api`:

- acquires a PostgreSQL advisory lock so concurrent instances do not migrate simultaneously;
- records applied migrations and SHA-256 checksums in `schema_migration`;
- refuses to silently accept modifications to already-applied migration files;
- applies each pending migration transactionally.

Production API startup runs this migration check before loading the compiled NestJS entry point. In memory mode it exits immediately without database work.

Migration `013_drop_ephemeral_room_storage.sql` removes the former PostgreSQL room, room-membership, House-room link, comment, and reaction tables. Room ownership by a House is now a property of the live in-memory room; the House itself and its membership remain durable in PostgreSQL.

## Realtime behavior

LiveKit is used for microphone, camera, screen sharing (including browser-supported shared audio), participant state, active-speaker feedback, stage reactions, and realtime comment delivery.

Comments, replies, pins, and emoji reactions are shared through LiveKit and retained by the API for the lifetime of the room. A newly joined or reloaded client hydrates the latest shared room history from the API, while browser storage remains a continuity/fallback layer. This history is deliberately discarded when the room finishes or the API restarts.

## CI

Pull requests and pushes to `main` run `npm run check`, covering:

- operational Node script syntax;
- shared contracts build;
- Angular web build with strict template checking;
- NestJS API build under strict TypeScript settings;
- React Native TypeScript checking.

The compiled API smoke suite boots the production API build against a pinned local LiveKit server. It verifies room creation and lifecycle, identity/slug behavior, House-scoped room-name rules, House profile authorization, joins, shared comment/reply/reaction state, pinning, and explicit-leave authorization/cleanup. CI separately compiles the Android native host.

The pull request remains the integration boundary; do not merge incomplete native/authentication work as production-ready.
