# Live Discussions

Cross-platform live discussion rooms with Clubhouse-style roles, camera, screen sharing, reactions, comments, Houses, and first-class browser support.

## Architecture

- **Web:** Angular, standalone/lazy features, signals, typed reactive forms
- **Mobile:** React Native
- **API:** NestJS
- **Realtime media/data:** LiveKit
- **Persistence:** PostgreSQL, with an in-memory development/test fallback
- **Workspace:** Nx monorepo
- **Shared contracts:** `@live-discussions/contracts`

The Angular application is split by feature (`home`, `houses`, `rooms`) with page components delegating use cases to facades and data-access services. NestJS owns room identity, authorization, role resolution, and LiveKit token/permission issuance.

## Room lifecycle

Each room has two distinct identifiers:

- an immutable server-generated UUID used internally and as the LiveKit room name;
- a human-readable slug used by the browser route: `/room/<room-name>`.

Room slugs are generated by the API. A room record remains available until an owner/moderator closes it. Closing a room deletes the LiveKit room, disconnects connected participants, and deletes the application room record. Browser clients remember whether a participant entered from Home or a House so Leave/Close returns that participant to the appropriate screen.

Participant role and stage/audience presence are persisted separately. Reloading a room therefore reconnects the same user to the same room and restores their role and stage position while the backing application data still exists.

## Development identity

Authentication is currently development scaffolding. The web/mobile clients send:

- `x-dev-user-id`
- `x-dev-display-name`

The API owns all role/permission decisions; clients cannot choose their room role. These headers are **not production authentication** and must be replaced before treating the deployment as secure for untrusted users.

## Environment

Copy `.env.example` to `.env` and configure LiveKit:

```bash
cp .env.example .env
```

Required LiveKit variables:

```text
LIVEKIT_URL=wss://<project>.livekit.cloud
LIVEKIT_API_KEY=...
LIVEKIT_API_SECRET=...
```

Persistence defaults to memory:

```text
DATABASE_DRIVER=memory
```

For PostgreSQL:

```text
DATABASE_DRIVER=postgres
DATABASE_URL=postgresql://...
```

`DATABASE_DRIVER=memory` is intentionally ephemeral: an API restart/redeploy loses rooms, memberships, Houses, and roles. Use PostgreSQL for durable server-side persistence.

## Install and run

The repository targets Node `22.23.1` and npm `10.9.8`.

```bash
npm install
npm run api
npm run web
```

Useful commands:

```bash
npm run check            # operational script checks + contracts/web/API build + mobile typecheck
npm run build:web
npm run build:api
npm run build:contracts
npm run typecheck:mobile
npm run migrate:api      # applies PostgreSQL migrations; no-op in memory mode
```

## Database migrations

Ordered migrations live in `apps/api/migrations`.

`npm run migrate:api`:

- acquires a PostgreSQL advisory lock so concurrent instances do not migrate simultaneously;
- records applied migrations and SHA-256 checksums in `schema_migration`;
- refuses to silently accept modifications to already-applied migration files;
- applies each pending migration transactionally.

Production API startup runs this migration check before loading the compiled NestJS entry point. In memory mode it exits immediately without database work.

## Realtime behavior

LiveKit is used for microphone, camera, screen sharing (including browser-supported shared audio), participant state, active-speaker feedback, stage reactions, and realtime comment delivery.

Comment history is currently cached per browser for continuity on refresh/re-entry; it is not yet durable shared chat history for users who were offline when a comment was sent. Durable cross-client comment history should be moved to server/database persistence when that becomes a product requirement.

## CI

Pull requests and pushes to `main` run `npm run check`, covering:

- operational Node script syntax;
- shared contracts build;
- Angular web build with strict template checking;
- NestJS API build under strict TypeScript settings;
- React Native TypeScript checking.

The pull request remains the integration boundary; do not merge incomplete native/authentication work as production-ready.
