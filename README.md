# Live Discussions

Cross-platform live discussion rooms with Clubhouse-style roles, camera, screen sharing, reactions, comments, Houses, and first-class browser support.

## Architecture

- **Web:** Angular, standalone/lazy features, signals, typed reactive forms
- **Mobile:** React Native
- **API:** NestJS
- **Realtime media/data:** LiveKit
- **Persistence:** PostgreSQL, with an in-memory development/test fallback
- **Workspace:** Nx monorepo
- **Shared contracts:** `@live-discussions/contracts`

The Angular application is split by feature (`home`, `houses`, `rooms`) with page components delegating use cases to facades and data-access services. NestJS owns room identity, authorization, role resolution, and LiveKit token/permission issuance.

## Room lifecycle

Each room has two distinct identifiers:

- an immutable server-generated UUID used internally and as the LiveKit room name;
- a human-readable slug used by the browser route: `/room/<room-name>`.

Room slugs are generated by the API. A room record remains available until an owner/moderator closes it. Closing a room deletes the LiveKit room, disconnects connected participants, and deletes the application room record. Browser clients remember whether a participant entered from Home or a House so Leave/Close returns that participant to the appropriate screen.

Participant role and stage/audience presence are persisted separately. Reloading a room therefore reconnects the same user to the same room and restores their role and stage position while the backing application data still exists. Client-side navigation from one room slug to another explicitly tears down the previous LiveKit session before joining the next room.

## Development identity

Authentication is currently development scaffolding. The web/mobile clients send:

- `x-dev-user-id`
- `x-dev-display-name`

The API owns all role/permission decisions; clients cannot choose their room role. These headers are **not production authentication** and must be replaced before treating the deployment as secure for untrusted users.

## Environment

Copy `.env.example` to `.env` and configure LiveKit:

```bash
cp .env.example .env
```

Required LiveKit variables:

```text
LIVEKIT_URL=wss://<project>.livekit.cloud
LIVEKIT_API_KEY=...
LIVEKIT_API_SECRET=...
```

Persistence defaults to memory:

```text
DATABASE_DRIVER=memory
```

For PostgreSQL:

```text
DATABASE_DRIVER=postgres
DATABASE_URL=postgresql://...
```

`DATABASE_DRIVER=memory` is intentionally ephemeral: an API restart/redeploy loses rooms, memberships, Houses, roles, and backend-shared comment history. Use PostgreSQL for durable server-side persistence.

## Install and run

The repository targets Node `22.23.1` and npm `10.9.8`. A committed npm lockfile is the dependency source of truth, so use `npm ci` for reproducible installs.

```bash
npm ci
npm run api
npm run web
```

Useful commands:

```bash
npm run check            # operational script checks + contracts/web/API build + mobile typecheck
npm run build:web
npm run build:api
npm run build:contracts
npm run typecheck:mobile
npm run migrate:api      # applies PostgreSQL migrations; no-op in memory mode
npm run mobile           # Metro bundler
npm run mobile:ios       # preflights the native iOS host project described below
npm run mobile:android   # preflights the native Android host project described below
```

CI and Render builds also use `npm ci` so they install the dependency graph recorded in `package-lock.json` rather than resolving a new graph on each build.

## React Native host setup

The repository currently contains the React Native JavaScript/TypeScript application, Nx targets, LiveKit dependencies, and `registerGlobals()` setup, but it does **not** yet commit `apps/mobile/ios` or `apps/mobile/android`. The `run-ios` and `run-android` targets therefore remain incomplete until native host projects are generated and reviewed.

`npm run mobile:ios` and `npm run mobile:android` run a native-host preflight first and report the missing platform directory with a pointer back to this setup section instead of failing later inside Nx.

Use the matching `@nx/react-native` generator on a clean branch to create/regenerate the native host projects. The Nx native upgrade generator replaces the iOS/Android native folders, so generated changes should be reviewed before committing.

After the native hosts exist, complete the LiveKit native integration:

- **Android:** call `LiveKitReactNative.setup(...)` from `MainApplication` before the normal React Native initialization. Add camera/microphone permissions (`CAMERA`, `RECORD_AUDIO`, `MODIFY_AUDIO_SETTINGS`) when publishing those tracks. Android screen share additionally requires the media-projection foreground-service permission.
- **iOS:** call `LivekitReactNative.setup()` from `AppDelegate`. Add `NSCameraUsageDescription` and `NSMicrophoneUsageDescription` to `Info.plist` before publishing camera or microphone. iOS screen sharing requires a Broadcast Extension.

The mobile join screen makes the API base URL editable. Its development defaults are:

- Android emulator: `http://10.0.2.2:3000`
- iOS simulator: `http://localhost:3000`

A physical phone must use a reachable LAN address or the hosted API URL instead of localhost.

## Database migrations

Ordered migrations live in `apps/api/migrations`.

`npm run migrate:api`:

- acquires a PostgreSQL advisory lock so concurrent instances do not migrate simultaneously;
- records applied migrations and SHA-256 checksums in `schema_migration`;
- refuses to silently accept modifications to already-applied migration files;
- applies each pending migration transactionally.

Production API startup runs this migration check before loading the compiled NestJS entry point. In memory mode it exits immediately without database work.

## Realtime behavior

LiveKit is used for microphone, camera, screen sharing (including browser-supported shared audio), participant state, active-speaker feedback, stage reactions, and realtime comment delivery.

Comments, replies, and emoji reactions are also persisted through the API. A newly joined/reloaded client hydrates the latest shared room history from the backend, while the browser cache remains a continuity/fallback layer. In memory mode this shared history is still lost when the API process restarts; PostgreSQL makes it durable across restarts.

## CI

Pull requests and pushes to `main` run `npm run check`, covering:

- operational Node script syntax;
- shared contracts build;
- Angular web build with strict template checking;
- NestJS API build under strict TypeScript settings;
- React Native TypeScript checking.

The compiled API smoke test also boots the production API build and verifies room identity/slug behavior, House-scoped room-name rules, House profile authorization, joins, and shared comment/reply/reaction persistence.

The pull request remains the integration boundary; do not merge incomplete native/authentication work as production-ready.
